# FINN Research subsystem assessment

## Purpose and scope

This assessment records the Research architecture before the approved Phase 1 work and maps it to the ENAM build challenge and the existing product revision backlog. It is not authorization to replace the Research subsystem.

The challenge asks for source-grounded company research using primary documents, with examples including annual reports, concall transcripts, quarterly comparisons, management guidance versus results, and bull-versus-bear analysis. It explicitly favors a focused, working investor workflow. The repository backlog says its priorities are planning guidance and do not authorize implementing them feature by feature.

## Current evidence in the repository

- The Research view is part of the existing FINN single-page application in `frontend/src/App.tsx`; it is not a separate app.
- The backend is the existing FastAPI application in `backend/app/main.py`. Research routes are mounted directly on it and share the application's deployment and data paths.
- The document library currently contains 11 manifest records. The reports data contains 44 unified evidence records, 43 legacy financial records, and one legacy commitment record. These are existing user/demo data and must be preserved during any migration.
- The backend has retrieval and intelligence tests in `backend/tests/`. They were inspected but not run as part of this assessment.
- The codebase has no authentication or login/session middleware that I could identify. Research currently follows the same app-level access model as the rest of FINN.
- Research documents and evidence are stored as JSON plus PDF files under `data/reports`. The README notes that a Render free instance has ephemeral storage, so uploads and edits can be lost on restart or redeploy.

“Works” below means the code path and caller/contract are present and internally connected. It does not mean that live NSE/model integrations or every upload scenario were exercised in this review.

## Preserve/reuse/refactor/replace summary

- **Reuse:** FastAPI monolith and app startup; existing Research routes; JSON/PDF data and document IDs; financial evidence model; model provider; current frontend navigation and Research API client.
- **Refactor:** PDF extraction rules; lexical ranking; large `App.tsx` Research section; inline Research API logic; duplicated model/citation synthesis path.
- **Replace:** Nothing is justified for Phase 1 from the inspected brief. No working service or existing data should be deleted or replaced.

## Phase 1 scope status

The challenge PDFs do not define a “Phase 1”; the user subsequently approved and defined Phase 1 as Research Reliability. The authorized work is page-aware extraction and chunking, relevance/scope correctness, end-to-end Ask FINN reliability, grounded answers and citations, and regression tests. The implementation is recorded in `backend/app/services/research/documents.py` and `backend/app/services/research/engine.py`; it preserves the existing API, storage, and user data. Automatic document discovery remains out of scope.

## Explicit constraints for follow-on work

1. Do not create a parallel Research app, service, or data store.
2. Do not remove or rename existing Research routes, JSON files, PDF uploads, portfolio, announcements, alerts, or app navigation as part of a Research-engine change.
3. Keep manual values visibly manual; do not imply automatic extraction.
4. Keep primary-source citations tied to document, reporting period, page, and excerpt.
5. Treat authentication as an application-wide concern: no auth mechanism was found in the current codebase, so a Research-only auth layer would create an inconsistent architecture.
